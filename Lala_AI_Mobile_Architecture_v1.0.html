Target Platforms: Android & iOS (Flutter Cross-Platform Engine) Document Version: 1.0 Date: September 2026 Status: Proposed Mobile Architecture

Executive Summary & Scope

This document defines the Mobile Application Architecture for Lala AI, a cross-platform content creator copilot built using Flutter. The architecture focuses strictly on the mobile application structure for Android and iOS, including presentation, state management, domain logic, security, social integrations, voice processing, and client API communication.

NOTE: This document strictly covers the Flutter mobile client application. Server infrastructure and backend microservices are excluded.

1. Flutter App Architecture

The Lala AI Flutter application follows a decoupled Clean Architecture combined with Feature-Driven Modularization. The application separates code into three core architectural layers (Presentation, Domain, and Data), supported by shared core modules and utilities.

Layer Separation & Responsibilities

Presentation Layer

  • UI Views & Widgets: Renders Material/Cupertino widgets, handles layout responsiveness, and displays interactive components (e.g. `MessageComposer`, `VoiceSheet`, `PlatformCard`).
  • State Management (Controllers): Manages screen states in volatile memory, captures user inputs, triggers business operations, and updates the UI reactively.

Domain Layer

  • Entities: Pure Dart objects representing core domain models (e.g. `UserEntity`, `ChatMessageEntity`, `ChannelMetricsEntity`). Free from Flutter framework dependencies.
  • Repository Contracts (Interfaces): Defines abstract contracts for fetching and mutating data via API services without framework coupling.

Data Layer

  • Data Transfer Objects (DTOs / Models): Contains JSON serialization/deserialization logic (`fromMap`, `toMap`, `fromJson`).
  • Repository Implementations: Implements domain interfaces, routing API requests through remote data sources.
  • Data Sources: Wrappers around HTTP network clients and secure token storage services.

UI View States (Loading, Success, Error, Empty)

All async operations use a standardized view state model:

enum ViewStatus { initial, loading, success, error, empty }

class ViewState {
  final ViewStatus status;
  final T? data;
  final String? message;


ViewState.loading() : status = ViewStatus.loading, data = null, message = null;
  ViewState.success(this.data) : status = ViewStatus.success, message = null;
  ViewState.error(this.message) : status = ViewStatus.error, data = null;
  ViewState.empty() : status = ViewStatus.empty, data = null, message = null;
}

  • Loading State: Displays shimmers or localized activity indicators while keeping the navigation header interactive.
  • Success State: Renders data widgets.
  • Error State: Renders error illustrations with clear retry actions (`CW.commonBtn(title: "Retry")`).
  • Empty State: Renders friendly contextual placeholders when API responses return empty arrays (e.g. `"No saved scripts yet"`).

4. API Integration

The application uses REST APIs for retrieving and submitting application data. Based on the current requirements, no offline database or local chat cache is included in the proposed architecture.

Mobile-Side API Data Flow

sequenceDiagram autonumber participant UI as Flutter View participant Ctrl as GetX Controller (ChatController) participant Repo as ChatRepository Implementation participant API as ApiService (HTTP Client)

UI->>Ctrl: User Opens Chat / Sends Prompt Ctrl->>Ctrl: Set State = ViewStatus.loading Ctrl->>Repo: sendChatMessage(chatId, promptText) Repo->>API: post('/chats/messages', body) API-->>Repo: ApiResponse.success(ChatMessageDto) Repo->>Repo: Map ChatMessageDto -> ChatMessageEntity Repo-->>Ctrl: Return ChatMessageEntity Ctrl->>Ctrl: Append to RxList in memory & Update ViewStatus.success Ctrl-->>UI: Re-render UI View

Component Placement Rules

  • API Models / DTOs (`lib/app/data/models`): Parses raw JSON payloads into strongly-typed Dart objects (`fromJson`/`toJson`). Includes null safety fallback logic.
  • API Services (`lib/networking`): Low-level HTTP engine managing timeouts (15s), Bearer token injection, logging, and standard HTTP exception parsing.
  • Repositories (`lib/app/data/repositories`): Executes HTTP API requests and maps DTOs directly to pure Domain Entities.
  • Domain Entities (`lib/app/domain/entities`): Frame-independent business models consumed by GetX Controllers in memory.

5. Local Storage & Database Architecture

To keep the mobile application lightweight and secure, the current architecture does not require an offline database or local chat cache. Chat history, conversations, content scripts, and creator channel analytics are retrieved through application APIs when required.

Storage Strategy & Component Classification

Local Database Decision

Local Database: TBD / Not currently required

The current mobile architecture does not require a dedicated local relational or NoSQL database. Local persistence is limited to secure session information and lightweight application preferences.

If future requirements introduce offline chat history, drafts, or offline-first functionality, a local database can be introduced after confirming the data model and offline requirements. The database technology should be selected at that stage rather than being assumed in the current architecture.

6. Authentication & Security

Security enforces a Zero-Trust client architecture to protect creator channel data and API tokens.

Authentication & Token Refresh Flow

sequenceDiagram autonumber participant App as Mobile App HTTP Interceptor participant Sec as Flutter Secure Storage participant API as Auth API Service

App->>API: Request user data (Access Token) API-->>App: 401 Unauthorized (Token Expired) App->>Sec: Retrieve Stored Refresh Token App->>API: Refresh session request alt Refresh Successful API-->>App: 200 OK (New Access & Refresh Tokens) App->>Sec: Save New Tokens App->>API: Re-try original request API-->>App: 200 OK (Profile Data) else Refresh Token Expired / Invalid API-->>App: 403 Forbidden App->>Sec: Purge Tokens & Clear In-Memory Controllers App->>App: Redirect to Authentication View + Show Toast end

Security Measures

1. Secure Token Storage: JWT access and refresh tokens are encrypted using `EncryptedSharedPreferences` on Android and iOS `Keychain` via `FlutterSecureStorage`. 2. Session Cleanup on Logout: Executing logout clears all secure tokens from `FlutterSecureStorage`, flushes UI preferences in `SharedPreferences`, purges all in-memory controller states, and redirects to the login screen. 3. Secure API Transport: Enforces HTTPS over TLS 1.3 for all REST interactions. Sensitive credentials (OAuth secrets, client secrets) are never stored inside the Flutter codebase. 4. Certificate Pinning: Marked as TBD / To Be Confirmed subject to API domain deployment.

Lala AI supports dual-modal interaction: typed text input and continuous voice speech recognition.

Multilingual Voice Strategy

Native Speech-to-Text Engine (`speech_to_text: ^7.4.0`)

  • Utilizes native OS speech recognition frameworks (Apple Speech Framework on iOS and Google On-Device Speech Recognition on Android).
  • Automatically detects user device locale (e.g., `en_US`, `hi_IN`, `mr_IN` for English, Hindi, Marathi).

Unified Language Handling

  • Transcribed text (regardless of script e.g. English, Devanagari) is sent directly to the API service. The language processing model handles multi-lingual intent understanding without requiring separate per-language code paths in Flutter.

Text-To-Speech (TTS)

  • Marked as TBD / To Be Confirmed pending client approval on whether responses should be read aloud natively via `flutter_tts`.
